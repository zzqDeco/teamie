# Production delivery

There is one deployed environment, **production**. Hosted CI uses disposable PostgreSQL/Redis containers and local service processes; it does not create another deployment. `main` is the only branch for ongoing work. Every `release/vMAJOR.MINOR.PATCH` branch and `vMAJOR.MINOR.PATCH` tag is a permanent archive: never append commits, force-push, rename, reuse, or delete it. A correction requires a new version cut from checked `main`.

## Repository setup

Release jobs build `teamie-identity`, `teamie-chat`, `teamie-realtime`, `teamie-web`, `teamie-agent-control`, `teamie-agent-runtime`, `teamie-llm-gateway`, `teamie-sandbox`, and `teamie-sandbox-runner` in private Alibaba Cloud Container Registry (ACR) repositories. Hosted runners also mirror Caddy, PostgreSQL 17, and Redis 7.4 to `teamie-caddy`, `teamie-postgres`, and `teamie-redis` in the same namespace. Production pulls all twelve images from ACR. Every manifest records the resolved digest, including infrastructure images. Infrastructure patch tags are resolved anew when creating a release; no mutable tag is used by Compose.

Use an existing ACR instance, preferably in the ECS region (`cn-shenzhen` for the current host), and create these twelve private repositories in one namespace. Configure these repository Actions variables before creating a new release branch:

| Variable | Value |
| --- | --- |
| `ACR_REGISTRY_PUBLIC_HOST` | Public ACR hostname, without scheme or path |
| `ACR_REGISTRY_PULL_HOST` | The same hostname, or its corresponding VPC hostname after verifying ECS access |
| `ACR_NAMESPACE` | Namespace containing the twelve `teamie-*` repositories |

Actions builds and pushes through the public endpoint. The manifest records the production pull endpoint with the same namespace, repository and digest; public and VPC addresses must identify the same instance and region. The workflow validates this pair before sending any registry credential. Enterprise VPC access requires an existing VPC binding and DNS configuration; choosing a VPC hostname alone does not establish connectivity. Personal Edition has shared-resource quotas and no SLA; the operator chooses the existing instance or approves any paid Enterprise instance separately.

Store a dedicated publisher's `ACR_PUSH_USERNAME` and `ACR_PUSH_PASSWORD` as repository Actions secrets. Grant it access only to the Teamie namespace/repositories. New ACR publishing does not use `GITHUB_TOKEN` package-write permission. Keep historical GHCR packages readable with `GITHUB_TOKEN` for compatible manual rollback; no archived image reference is rewritten.

Create the GitHub Environment named `production`. Permit release branches `release/v*` and `main` (the latter is needed only for manual rollback). Store these secrets in it:

| Secret | Value |
| --- | --- |
| `PRODUCTION_SSH_HOST` | Production IP/hostname |
| `PRODUCTION_SSH_USER` | `teamie-deploy` |
| `PRODUCTION_SSH_KEY` | Dedicated SSH private key |
| `PRODUCTION_SSH_KNOWN_HOSTS` | Host key pinned after verification through a trusted channel |
| `ACR_PULL_USERNAME` | Dedicated identity with read access to the Teamie repositories |
| `ACR_PULL_PASSWORD` | Its ACR registry credential, not an Alibaba Cloud account password or AccessKey |

Do not populate known_hosts from an unverified network scan during deployment. No persistent Actions runner is needed. The production job sends registry credentials through SSH stdin; the host selects the correct provider only after validating the retained manifest, logs in with `--password-stdin`, pulls all digests using a private temporary `DOCKER_CONFIG`, and removes it before starting services. Registry credentials are neither application environment variables nor release-bundle contents. Manual rollback receives a separate short-lived `GITHUB_TOKEN` for historical GHCR manifests; ACR credentials are never sent to GHCR. If a GitHub plan cannot create Environments, equivalent repository secrets can be used after removing only the workflow `environment` binding; retain the single serialized production job and manual branch guard.

Configure server-side rules to prohibit updates, deletion and force-push of `release/v*`, prohibit tag updates/deletion for `v*`, and require passing CI plus review for `main` where the account plan supports these rules. The current private GitHub Free repository does **not** have effective server-side branch/tag protection: the attempted API configuration was denied by plan restrictions. The release workflow rejects non-creation pushes and checks archive SHA before deployment and publication, but an owner with repository write access can still mutate Git refs. This workflow guard is not server-enforced immutability. Never enable automatic release-branch deletion.

## Host provisioning

The operator runs `ops/bootstrap.sh` as root on Debian 13 x86_64. It installs Docker Engine/Compose from Docker's official signed APT repository and creates the dedicated delivery user and private directories. It preserves existing authorized keys and refuses conflicting unofficial container packages. Add only the delivery **public** key to `/home/teamie-deploy/.ssh/authorized_keys`; restrict that entry with `restrict` (no port forwarding, agent forwarding, X11 forwarding or PTY). Docker group membership gives host-level control and is reserved for this delivery account. Only SSH and Caddy's TCP 80/443 and optional UDP 443 should be allowed through the cloud security group. PostgreSQL, Redis, RPC and application ports remain on the private container network.

Create `/srv/teamie/config/production.env` from `deploy/production.env.example`, owned by `teamie-deploy`, mode `0600`. Supply six independent random URL-safe values for the PostgreSQL admin and the five application roles. Corresponding service URLs must use exactly `teamie_identity`, `teamie_chat`, `teamie_agent_control`, `teamie_agent_runtime` and `teamie_gateway` database/role names; do not use the administrator role in an application. Initialization creates these databases on a new volume. The explicit deployment upgrade gate also creates missing roles/databases on an existing volume, verifies ownership and least privilege, and checks every supplied role password through a TCP login. Existing roles, passwords, tables and rows are preserved. Changing the environment later does not rotate an existing database password; rotate the role and its protected URL together in a reviewed operation.

Set `SITE_ADDRESS` and `APP_ORIGIN` to the same HTTPS origin without a trailing slash, initially `https://PUBLIC_IP`. Set `TLS_SERVER_NAME` to that origin's host/IP only, without scheme or port. Caddy uses it as `default_sni`: IP HTTPS clients omit SNI, and a container's local address differs from the public certificate IP. Without this default, an otherwise valid public-IP certificate can fail selection before HTTP begins. Deployment validation requires the value to match the public origin's hostname. Production Compose always sets `COOKIE_SECURE=true`. `BOOTSTRAP_INVITE_CODE` is optional and defaults to `teamie-bootstrap` when unset or empty; a configured nonempty code may override it. Only when there are no accounts can this code create the first account, which atomically becomes platform admin. Afterward the bootstrap code no longer registers accounts. That administrator creates ordinary registration invitations at `/app/admin`; each invitation is cryptographically random, stored only as a hash, expires after seven days and can be consumed by exactly one successful registration. Admin-generated registration invitations are separate from per-workspace invitations. Public signup cannot bypass this requirement even if its host flag is true. The first admin receives no implicit access to other users' workspaces. User passwords must be 12 characters or more and at most 72 UTF-8 bytes with the current bcrypt implementation.

Copy `deploy/feature-flags.default.json` to `/srv/teamie/config/feature-flags.json` (mode `0644` so non-root service users can read the bind mount). Backend capabilities are the intersection of implementation, flag and permission. Persisted messages and conversations remain readable when a write flag is disabled. To change flags, update this host file atomically, change its `revision`, and restart Identity, Chat, Realtime, Agent Control and Agent Runtime using the current protected Compose/image configuration. Audit the change without copying secrets to logs. Flags are not stored in images; every successful deployment records the actual runtime flag hash and revision in its private deployment record.

For the public IP, copy `deploy/tls/acme-ip.caddy` to `/srv/teamie/tls/issuer.caddy` (mode `0644`). It explicitly selects the Let's Encrypt production ACME issuer with the `shortlived` profile, avoiding Caddy's locally trusted IP default and persisting renewal state in the Caddy data volume. Both 80 and 443 must be externally reachable for validation. Caddy renews these short-lived certificates automatically; monitor certificate expiry and renewals. A deployment is not successful until ordinary certificate-verifying curl reaches the public origin. No `--insecure` option or HTTP production cookie fallback is used.

Alternatively, have the root operator provision `/srv/teamie/tls/certs/` as **root:root mode `0700`**, its `privkey.pem` as **root:root mode `0600`**, and `fullchain.pem` as **root:root mode `0644`**, then use `deploy/tls/certificate-files.caddy` as the host issuer snippet. This ownership is required: Caddy runs as container UID 0 with capabilities dropped, so a private key owned by `teamie-deploy` is unreadable. Bootstrap preserves an existing certificate directory's ownership. The deployment script checks the actual owner/mode and read access inside a temporary container using Caddy's production UID and capabilities, without displaying certificate/key contents. Keep all parent directories private. Its certificate SAN must cover the public address. The external renewal process must preserve those owners/modes and restart Caddy. Never commit or bundle keys/certificates or a completed production environment file.

Total resident service memory caps are 1,280 MiB: Caddy 64, web 32, Identity 96, Chat 192, Realtime 128, PostgreSQL 384, Redis 64, Agent Control 64, Agent Runtime 128, Model Gateway 64 and Sandbox supervisor 64. One active Sandbox child adds at most 128 MiB, so the peak container budget is 1,408 MiB. Concurrency starts at one for the runtime worker, gateway request and Sandbox job. On this roughly 1.75 GiB usable host the remaining memory is reserved for Debian, Docker and filesystem cache; monitor actual pressure before raising any limit. Redis is disposable, has a 40 MiB key limit and no persistence. PostgreSQL data and Caddy ACME state use named persistent volumes. Logs rotate at 10 MiB × 3 per service. Do not run `docker compose down --volumes` or indiscriminate volume/image pruning on production.

## Release sequence

1. Merge reviewed work into `main`; require all current-SHA CI checks: web lint/build, backend authorization/persistence tests and vet/build, disposable full HTTP/WebSocket acceptance, Linux container builds, and delivery validation.
2. Fetch `main`, check the exact SHA and create `release/vX.Y.Z` at that SHA. Push the branch once. Keep it forever.
3. `Release production` accepts only a newly created semantic-version branch whose SHA exactly equals current `main`. It reruns CI, builds nine application/execution images and mirrors three infrastructure images to ACR with unique build tags, then writes `release-manifest.json`. The manifest identifies source ref/SHA/version, database schema versions/storage major, default flag revision/hash, the ACR endpoint/namespace contract, and twelve immutable image digests, including the execution runner. Historical manifests without ACR metadata retain their original GHCR contract.
4. Immediately before SSH, the job re-queries `main` and the archive ref. GitHub concurrency serializes production deploy/rollback jobs, and a host `flock` serializes migrations, rollout and the final state change. The host rejects stale manifests, version downgrades, incompatible schema changes and same-version image/source replacement. A high-water version remains after rollback so a delayed release cannot undo a newer deployment.
5. Before replacing an existing deployment, make a local logical backup. Pull all images first. Start PostgreSQL/Redis, provision any missing owned databases without modifying existing data, stop the old Agent Runtime writer, then Identity (its migration), Chat (its migration), Realtime/web, Agent Control/Gateway/Sandbox, Agent Runtime and Caddy; each readiness check must pass before proceeding. Verify every running container uses its exact manifest image and each Go service reports its expected version/SHA. Verify public HTTPS and the unauthenticated auth route. Only then atomically switch `/srv/teamie/current` to a complete deployment record and preserve `/srv/teamie/previous`.
6. Only after the deployment job succeeds does the publication job create the permanent tag and GitHub Release with the manifest attached. Failed builds/rollouts do not create a release tag. The publication job re-checks the release archive's SHA. A failed compatible rollout attempts to restore the previous container images; an incompatible migration is never reversed automatically.

`/srv/teamie/current/release-manifest.json` identifies the running release. Its `deployment.json` records operation, time and the actual runtime flag identity. `recipe` points to the immutable uploaded deployment files; `images.env` contains only digest references. Successful manifests remain under `/srv/teamie/state/history/`, and the highest deployed forward version is retained in `state/highwater.json`. Uploaded archives contain only `deploy/`, `ops/` and the non-secret manifest. They never contain host environment files, databases, runtime state or SSH keys.

Single-host service replacement can briefly interrupt connections; the client must reconnect and run durable sync. Passing build or readiness gates does not by itself prove end-user behavior. The production acceptance run remains a separate check of registration/login, invitations, authorization, idempotence, message order and reconnect behavior. Before release, CI also generates a disposable IP-SAN certificate and verifies the production Caddy global TLS settings through a different loopback socket address using `curl --cacert --connect-to`; the TLS ClientHello must have empty SNI, trusted IP verification must pass and HTTP redirects must still work. This checks certificate selection locally; it does not prove Let's Encrypt issuance, renewal or production reachability.

## Rollback

Run `Roll back production images` through `workflow_dispatch` **on `main`**, supplying a previously successfully deployed `vX.Y.Z` and the full SHA currently reported by production. The production Environment and the same concurrency lock apply. A changed current SHA aborts the operation. The host selects a retained successful manifest; arbitrary uploaded rollback images are not accepted.

The job uploads the reviewed current delivery helpers to a fresh host directory so it can authenticate either ACR or legacy GHCR. It keeps the active deployment's Compose recipe and selects the target manifest only from successful history. It does not edit archived recipes, branches, tags or historical image references.

Rollback changes container images and the active release manifest. It preserves the current deployment recipe, production configuration, flags and database contents. It requires identical schema versions, PostgreSQL storage major and default flag contract. Forward migrations are never undone, and no database backup is automatically restored. If schemas differ, ship a new compatible forward release or prepare a separate, reviewed recovery procedure. The previous record is retained for inspection; rollback never deletes or rewrites a release branch/tag.

## Backup and recovery

`ops/backup.sh` derives the database list from the active manifest and takes custom-format logical dumps of every owned database (two in v0.1, five in v0.2), verifies each archive can be listed, saves the active release/deployment metadata and writes SHA-256 checksums. Each database has its own consistent snapshot; they are not a single cross-database transaction snapshot. Backups are mode `0600` in private directories, with seven days retained. A failed dump is removed and never advertised as a completed backup. Listing an archive is a structural check. Hosted CI additionally runs `ops/ci-restore.sh`: create the five isolated roles/databases, write rows and schema/binary fixtures, dump each database, restore it into a new disposable database, compare the restored values, and verify cross-service connection denial. This bounded real restore verifies the delivery tools; it does not assert that a particular production backup has been restored.

After the first successful release, the root operator may install `ops/teamie-backup.service` and `.timer` under `/etc/systemd/system/`, run `systemctl daemon-reload`, and enable/start `teamie-backup.timer`. It runs once daily at 18:15 UTC (02:15 Asia/Shanghai) with up to five minutes of jitter. Verify the unit user if a custom delivery username was used. Backups take a shared deployment lock, preventing a release from changing database containers during a dump. Every replacement deployment also takes a backup under the exclusive release lock.

These are **local backups on the same 40 GiB disk**, not disaster recovery against host or disk loss. Off-host encrypted copies, storage monitoring and tested restore procedures remain operator work. For recovery, stop application writes, preserve the current data and manifest, validate backup checksums, restore to new private databases/volumes with matching roles, run explicit integrity/authorization checks and only then switch traffic. Never restore over a running database as part of an image rollback.


## Agent infrastructure and v0.3 upgrade

The v0.3 manifest uses `manifestVersion: 2`, twelve image digests and schema vector `{identity:2,chat:2,agent_control:1,agent_runtime:2,gateway:2}`. v0.1/v0.2 archives remain valid; image-only rollback across different schema vectors is rejected. Preserve all release branches/tags and use forward migrations for existing accounts, workspaces, messages and encrypted Gateway configuration. Runtime migration 2 adds native task/event/outbox, checkpoint and serial-delivery metadata; Gateway migration 2 adds declared context capacity. No existing database is reset.

For an upgrade from v0.2, atomically preserve existing host flag values and add missing `agents.runtime.v3=true` and `agents.tasks.execute=true`, with revision `agents-v2`. Do not overwrite provider settings or internal credentials. Older flag files without these keys admit no new v0.3 work. Runtime RPC is private port 8885; owner HTTP/SSE stays behind Agent Control. The rollout stops the previous runtime writer before updating dependencies. Before the first async Sandbox upgrade, ensure legacy synchronous executions have quiesced; they do not have recoverable async receipts. Later async tasks remain daemon-owned during supervisor replacement and are adopted from exact receipt/name/labels, independently of HTTP/RPC transport lifetime.

Agent Control, Agent Runtime and Gateway each own a separate database/role on the existing PostgreSQL server. Only Gateway has an additional normal egress network for administrator-configured provider HTTPS. Its private HTTP admin routes require a human platform administrator session, trusted Origin and CSRF for writes. A configured endpoint must resolve entirely to public addresses; redirects, environment proxies and private/metadata destinations are denied on every connection. Model, request size, token count, timeout and concurrency limits remain gateway policy. Gateway usage records contain attribution and counters, not prompts, completions or keys, and retain at most roughly 100,000 rows / 30 days with bounded hourly pruning.

Generate five independent internal credentials of at least 24 characters: `AGENT_RUNTIME_TOKEN`, `IM_PRINCIPAL_CONTROL_TOKEN`, `IM_PRINCIPAL_RUNTIME_TOKEN`, `GATEWAY_RUNTIME_TOKEN`, `SANDBOX_RUNTIME_TOKEN`. `X-Teamie-Service-Key` uses `IM_PRINCIPAL_RUNTIME_TOKEN`; no extra service key exists. Gateway encrypts the saved provider API key with AES-256-GCM using `GATEWAY_MASTER_KEY` (exactly 64 hexadecimal characters). Retain that master key with protected configuration outside database dumps; losing it makes the encrypted provider key unrecoverable. Reads expose only `hasApiKey`; omitted keys preserve the saved value and explicit clear removes it. Initially leave the provider unconfigured: all services remain healthy and Agents wait with `model_unconfigured`. Save/test provider configuration later in `/app/admin/gateway`; test makes one small real request with the saved configuration. CI protocol fixtures do not configure or call a production provider.

Only the trusted Sandbox supervisor mounts `/var/run/docker.sock`. That access is equivalent to host administration, so its RPC stays private and requires its distinct runtime token. The fixed runner is pulled from the manifest; jobs cannot select images, mounts, environment secrets or networking. Children use UID/GID 10001, `network=none`, read-only root, all capabilities dropped, no-new-privileges, 0.5 CPU, 128 MiB RAM/no swap, 32 PIDs, 128 file descriptors, an 8 MiB per-file limit, a 16 MiB `/tmp` and 64 KiB combined output. The persisted workspace is one hash-derived bind mount per Agent. Protected roots `/srv/teamie/sandbox-workspaces` and `/srv/teamie/sandbox-state` are root:root 0700. The child receives neither receipts nor Docker/provider/IM credentials. A 2 GiB free-disk reserve and 10,000-receipt admission bound remain; these are not per-Agent disk quotas. Monitor growth and keep execution concurrency one.

Native runtime uses async Start/Get/ReadOutput/CancelTask. A protected fsynced intent precedes Docker create; output and cancellation intent survive restarts, and the terminal result is durable before container removal. Known tasks are adopted without rerunning commands; missing or ambiguous execution remains unknown. Supervisor shutdown detaches observation and preserves async children. No command deadline is imposed by default; an explicitly supplied deadline is bounded to 1–86400 seconds. Legacy synchronous Exec retains its default 30/max 60-second compatibility. Native workspace file APIs enforce `os.Root` confinement and use mutation receipts for write/edit/delete recovery. Runtime's native TaskStore implements Eino conformance contracts; task completion returns through a durable notification outbox into the single-writer Agent inbox.

Gateway unary calls retain a 50-second request deadline; actual streaming uses private NDJSON transport with a five-minute request deadline, cancellation, content/tool deltas and explicit terminal/error events. These are individual network-request lifetimes, not Agent work budgets. Metadata-only owner activity must not expose prompt, command, output, raw native events, credentials, attempts or fences. Admin `contextWindowTokens` defaults to 16384, accepts 4096–2000000 and preserves its value when omitted. Saving configuration does not make a provider request.

Database backups cover Gateway/Agent data after v0.2 activation. Sandbox workspaces/receipts are outside PostgreSQL and require a separate quiesced filesystem backup by the operator; never assume a DB-only dump contains them. Stop the worker and wait for/stop active execution before copying those two roots together. Keep the encrypted key's master key in protected configuration backup. Daily backups here remain local-only and do not protect against losing the host disk.
