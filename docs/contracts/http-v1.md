# IM API v1 — initial implementation contract

This file coordinates the initial frontend, backend and deployment. The machine-readable IDL source of truth lives in [`contracts/im/http_identity.thrift`](../../contracts/im/http_identity.thrift), [`contracts/im/http_chat.thrift`](../../contracts/im/http_chat.thrift), [`contracts/im/ws_realtime.thrift`](../../contracts/im/ws_realtime.thrift), and [`contracts/im/model.thrift`](../../contracts/im/model.thrift). JSON fields use camelCase, IDs are strings, timestamps are RFC3339 UTC. Responses are JSON objects (no success envelope). Errors use `{ "error": { "code": "forbidden", "message": "..." } }` with appropriate HTTP status. No Agent execution model appears in this API.

## Identity and session

- `POST /api/v1/auth/register` body `{email, password, displayName, inviteCode}` -> 201 `{user, csrfToken}` and login cookie. Registration is strictly invitation-only. When no accounts exist, only `BOOTSTRAP_INVITE_CODE` is accepted; its default is `teamie-bootstrap` if unset. That first account atomically becomes platform admin. After the first account exists, the bootstrap code is invalid for registration; only unused, unexpired, unrevoked admin-generated registration codes are accepted. Each ordinary code is consumed by exactly one successfully created user in the same transaction. Failed registration must not consume it. Concurrent requests must not create two bootstrap admins or spend one ordinary code twice. Password minimum 12 characters. Email uniqueness is case-insensitive.
- `GET /api/v1/auth/registration` -> `{mode:"invite",bootstrapRequired:boolean}`. Public, no-store, never returns any configured or generated invitation secret.
- `POST /api/v1/auth/login` body `{email,password}` -> `{user,csrfToken}` and cookie.
- `POST /api/v1/auth/password` body `{currentPassword,newPassword}` -> 204 without `Set-Cookie`. Only the current authenticated human account can change its own password, with the normal Origin and CSRF checks. The current password must match; the new password must differ, including under bcrypt comparison, and follow the registration limit of at least 12 Unicode code points and at most 72 UTF-8 bytes. Password replacement and revocation of every existing login session for that account commit atomically. A login that already checked the previous hash must not create a new session after the change. The revoked cookie can no longer authenticate; the browser clears its local login, CSRF token and data, then asks the user to sign in again. Omitting a cookie write prevents a delayed password response from deleting a newer login cookie. Incorrect current password returns 400 `invalid_current_password` and keeps the session; an invalid new password returns 400 `invalid_password`, an equivalent password returns 400 `password_unchanged`. Invalid or revoked sessions return 401. Rate limits apply. Passwords, hashes and session material never appear in response bodies or logs.
- Registration and password settings ask the user to confirm the new password in the browser. A mismatch is rejected before submitting; confirmation is a form check and is not sent as another credential field. Registration keeps its existing invitation-only API and atomic single-use invite consumption.
- `GET /api/v1/auth/session` -> `{user,csrfToken}` or 401.
- `POST /api/v1/auth/logout` -> 204 without `Set-Cookie`, revokes the stored session. A delayed logout cannot clear a newer login cookie; the revoked cookie is inert until a subsequent login replaces it. New-session creation also removes at most 1,000 expired session rows transactionally, skipping locked rows and preserving live sessions.
- `PATCH /api/v1/auth/profile` body `{displayName}` -> `{user}`.
- User: `{id,email,displayName,kind:"human",platformRole:"admin"|"user",createdAt}`. Reserve `kind:"agent"` in contracts only. Server derives sender ID and platform role from persisted identity; neither is accepted from registration input. Platform admin is separate from workspace owner and receives no implicit access to other workspaces' messages.
- Opaque random `teamie_session` cookie, HttpOnly, SameSite=Lax, Secure on production HTTPS. Writes after login require `X-CSRF-Token`; reject untrusted Origin. Login/register also reject untrusted Origin. WebSocket requires matching Origin and current session.
- The browser also sends its current `X-CSRF-Token` on authenticated HTTP reads. When supplied, the token must match the cookie session; a mismatch returns 401 `session_changed` before protected handlers run. Omitted read tokens remain compatible with existing non-browser clients. `/auth/session` is deliberately unbound so the browser can discover a changed cookie, discard account-bound caches and adopt the actual current account. Late protected responses from an earlier local session are discarded after body decoding. Login/register responses can still set a cookie after their form unmounts, so the browser reconciles with `/auth/session` rather than only ignoring their body. Ordinary 403 capability/owner denials refresh permissions without clearing all readable content.
- Edge responses use `Referrer-Policy: no-referrer`, including invitation landing pages, so invitation codes in an initial URL are not copied into subsequent same-origin asset/API Referer headers.

## Platform registration invitations

- Only authenticated `platformRole=admin` may call these Identity-owned APIs. They use the same CSRF/Origin enforcement as other writes.
- `GET /api/v1/auth/admin/invites` -> `{invites:[{id,createdAt,expiresAt,usedAt?,revokedAt?}]}`. Do not return raw codes after creation or password/token material. A consumed user's ID may be included as `usedBy` for the administrator.
- `POST /api/v1/auth/admin/invites` body `{}` -> 201 `{invite:{id,code,createdAt,expiresAt},url}`. Codes are cryptographically random, single-use, expire after seven days, and stored only as a hash. `url` is the frontend-relative `/login?mode=register&inviteCode=<code>`. Raw code is shown only in this response.
- `DELETE /api/v1/auth/admin/invites/:id` -> 204; revoke an unused code (idempotent). A used code stays used and can never become reusable. Every invitation is consumed atomically with account/session creation. Invalid/expired/revoked/used codes return a consistent invalid-invitation error.
- Frontend route `/app/admin` provides generation, one-time code/link copy, status list and revoke for platform administrators. The login registration form accepts `inviteCode` from the URL and explains initialization when `bootstrapRequired=true`.
- `auth.public_signup` remains an unsupported false capability in this release: setting it true in a host file cannot bypass invitations.

## Password recovery

- A signed-in human who remembers the current password continues to use account settings and `POST /api/v1/auth/password`. The login page links to `/forgot-password`, which directs the user to contact a platform administrator. There is no public email lookup, automated email delivery, invitation bypass or account creation in this recovery flow.
- `GET /api/v1/auth/admin/users?cursor=&limit=&q=` returns `{users:User[],cursor?:string}` for current enabled, undeleted human accounts. It requires a current human platform-administrator session. Results are bounded and cursor-paginated; `q` is a literal case-insensitive name/email filter of at most 200 Unicode characters. Passwords, credential hashes, sessions and reset secrets are never listed.
- `POST /api/v1/auth/admin/users/:id/password-reset-links` with `{}` returns 201 `{reset:{id,createdAt,expiresAt},url}`. It requires a current human administrator session plus normal Origin/CSRF checks, revalidated in the issuance transaction. `url` is the frontend-relative `/reset-password#token=<secret>` and is returned only at creation. An administrator may target their own account. Issuance changes neither passwords, roles nor existing login sessions.
- Reset links contain at least 32 cryptographically random bytes, are stored only as a hash, expire after one hour, and can successfully reset the password once. Generating a new link revokes that account's previous unused links. A successful ordinary password change also invalidates outstanding reset links. Disabled, deleted and Agent principals cannot receive a link.
- `/reset-password` keeps the fragment token in memory and removes it from the visible URL without losing it during React StrictMode setup/cleanup. It never puts the token into query strings, browser storage, analytics or shared query caches. The token authorizes the public reset operations; a login cookie is not required.
- `POST /api/v1/auth/password-reset/inspect` with `{token}` returns `{account:{id,displayName,emailMasked},expiresAt}`. It validates without consuming the link, so opening or inspecting the link cannot spend it. Invalid, expired, revoked and consumed links return the same 400 `invalid_reset_link` error.
- `POST /api/v1/auth/password-reset` with `{token,newPassword}` returns 204 without `Set-Cookie` or automatic login. It checks JSON content type and the existing Origin rules, validates the same password policy and bcrypt equivalence as ordinary changes, and atomically consumes the link, replaces the password, invalidates other outstanding links and revokes all target-account sessions. An invalid new password or failed transaction does not consume the link. Concurrent consumption, issuance, ordinary changes and in-flight logins serialize against the account's current credential. The frontend confirms the password locally and protects unrelated or newer login state from delayed responses.
- `auth.password_reset` gates new link issuance through both administrator APIs and the operator command. Existing valid links remain inspectable and redeemable when new issuance is disabled; the administrator's user list remains readable. The current default flag revision is `password-reset-v1`.
- An operator with server access can run `ops/password-reset-link.sh --email <account>` against the deployed Identity container. Its `/app/identityctl password-reset-link --email <account>` command uses the same issuance store, current feature flags and canonical `APP_ORIGIN`. It outputs only the newly generated absolute fragment URL and expiry as JSON; it does not set a password directly or grant a role. This also recovers an administrator who cannot sign in.
- Identity schema 3 adds the private reset-link ledger and preserves prior users, sessions and invitations. Other service schemas remain unchanged. Resetting a password never changes workspace membership or message ACLs.

## Chat bootstrap and workspaces

- `GET /api/v1/bootstrap` -> `{user,workspaces,conversations,capabilities,flagsRevision,syncCursor}`. `syncCursor` is informational; clients perform initial `/sync?cursor=0` and reconcile entity versions before adopting a new cursor, so bootstrap cannot introduce a message-loss window.
- Workspace: `{id,name,createdBy,createdAt}`.
- `POST /api/v1/workspaces` body `{name}` -> `{workspace,conversation}`. Creates membership and a default `general` channel atomically.
- `GET /api/v1/workspaces/:id/members` -> `{members:[{userId,displayName,role,kind}]}`. `role` is owner/member. Profiles may be resolved through Identity RPC.
- `POST /api/v1/workspaces/:id/invites` -> `{code,expiresAt}`. Owner only; return a frontend-relative `/join/<code>` link if useful.
- `GET /api/v1/invites/:code` -> `{workspace:{id,name},expiresAt}`. Public metadata only.
- `POST /api/v1/invites/:code/accept` -> `{workspace,conversations}`. Authenticated and idempotent membership admission.
- `DELETE /api/v1/workspaces/:id/members/:userId` -> 204. Owner only, cannot remove owner; removal revokes sends, reads and live delivery.

## Conversations and messages

- Conversation: `{id,workspaceId,type:"channel"|"direct"|"group",name,memberIds,lastSeq,readSeq,notificationLevel,updatedAt}`. All initial conversations belong to a workspace; direct/group membership is explicit. Workspace channels are accessible to current workspace members. `readSeq` and `notificationLevel` are caller-scoped; see [conversation notification levels](#conversation-notification-levels).
- `GET /api/v1/workspaces/:id/conversations` -> `{conversations}`.
- `POST /api/v1/workspaces/:id/conversations` body `{type,name?,memberIds?}` -> `{conversation}`. Owner creates channels; current members create direct/group when capability permits. Direct chat is unique per workspace+unordered participant pair; server includes current user.
- `GET /api/v1/conversations/:id/messages?beforeSeq=<n>&limit=50` -> `{messages,hasMore}` in ascending seq order. Omit beforeSeq for latest page. Optional `q` performs literal, case-insensitive keyword search across the authorized conversation before pagination (maximum 200 characters); retracted bodies never match. `beforeSeq` pages matching results. Optional `aroundSeq` returns a sequence neighborhood centered on a referenced message and cannot be combined with `beforeSeq`. These generic history parameters apply equally to humans and authenticated participants.
- Optional `content=files` on the same history route returns only messages with published, unretracted attachments. In this mode `q` matches literal, case-insensitive **filenames**, not captions; omitting `q` browses all delivered files in the authorized conversation. Results still use the normal Message shape, ascending sequence order and `beforeSeq` pagination. A result contains the whole ordered attachment group, even when only one filename matches. Pending uploads never appear. The browser shows matching files, retains the ordinary source message reference, and uses the existing authenticated download. `content=files` cannot be combined with `aroundSeq`; other nonempty `content` values and invalid/overlong search terms return 400 `invalid_query`. No database/schema or write admission flag changes are needed, and disabled uploads preserve search/read access to existing files.
- `POST /api/v1/conversations/:id/messages` body `{clientMessageId,body,replyToId?,attachmentIds?,mentions?}` -> `{message}` (201 first write / 200 retry). Text max 8000 characters; empty text is accepted with at least one attachment. Uniqueness `(senderId,clientMessageId)`. Conflicting retry body/conversation/reply/ordered attachment IDs or mention ranges/recipient IDs returns 409. Reply target must belong to same conversation. A committed retry remains readable after a write flag is disabled or a message is retracted.
- Message: `{id,conversationId,senderId,senderName,senderKind,clientMessageId,seq,body,replyToId?,attachments?,mentions?,reactions?,createdAt,editedAt?,retractedAt?}`. `attachments` is an ordered list of descriptors defined below. `reactions` is defined in [reactions](#reactions). `seq` is immutable message order. Edits/retracts use independently ordered sync events. Retracted bodies are omitted/empty and attachment descriptors are removed for every read, including old sync events.
- `PATCH /api/v1/conversations/:id/messages/:messageId` body `{body,mentions?}` -> `{message}`. Author only, feature gated.
- `DELETE /api/v1/conversations/:id/messages/:messageId` -> `{message}` tombstone. Author only, feature gated.
- `POST /api/v1/conversations/:id/read` body `{seq}` -> `{readSeq}`. Monotonic, bounded by conversation lastSeq.
- Optional `mentions:[{userId,start,end}]` on message sends and edits binds an `@label` span to an ordinary current conversation member, human or Agent. Offsets are half-open UTF-16 units of the exact untrimmed submitted body, matching browser selection positions; they must be integer code-point boundaries, ordered, non-overlapping, in range, and cover 2–181 Unicode characters starting with `@` with no CR/LF/tab. At most 32 ranges per message. Chat validates membership under the normal conversation lock and never infers sender identity or permission from labels. Duplicate names are disambiguated by ID; plain typed/pasted `@name` without a selection is ordinary text. This adds no notification service or access grant.
- `im.message.mentions` gates new annotations. Persisted annotations remain visible when disabled. Retry identity also compares immutable original mention ranges and IDs; omission means no annotations and conflicts with an originally annotated send. Edits replace the current annotation list (omission clears it) while preserving the original send identity. Retraction removes annotations from every read, including old sync events. Chat schema 5 adds current/original annotation columns without altering existing messages or upload receipts.
- The browser offers the current conversation's members through one keyboard/touch mention selector and marks Agent options with the existing tag. It sends selected IDs and rebases surviving ranges after text edits or trimming. Reply navigation uses the ordinary single-message read and `aroundSeq` history APIs when the target is not loaded; temporary context can return to the latest messages, and late responses after navigation/account changes are discarded.
- One conversation-header search button opens message/file modes on desktop and mobile. Message keywords search the whole currently authorized conversation, with literal matches highlighted as escaped text. File mode also supports an empty keyword for browsing. Results page independently of the normal timeline and do not mark messages read. Current sync edits/retractions update or remove matching rows. Switching query/mode/conversation/account or closing aborts outstanding requests and discards late responses. Selecting a source reuses ordinary message/context reads and returns focus to that message; there is no runtime resource exposure.
- `GET /api/v1/workspaces/:id/messages/search?q=&cursor=&limit=20` -> `{items:[{message,conversation:{id,workspaceId,name,type}}],cursor?}`. Requires current membership in workspace `:id` (non-members receive 404; humans and authenticated Agent principals follow the same ACLs). Searches workspace channels plus direct/group conversations in that workspace where the caller is a current member; neither platform administration nor workspace ownership bypasses private conversation membership. Reads acquire workspace and authorized conversation share locks in sorted order and recheck membership after waits, ordering them with revocations. `q` is trimmed and performs literal, case-insensitive matching (`strpos(lower(body),lower(q)) > 0`, 1–200 Unicode characters) against unretracted messages; retracted messages never match. Results sort newest first by immutable `(createdAt,id)` with an opaque descending cursor and `limit` 1–50 (default 20). Invalid/empty/overlong queries, page sizes or cursors return 400 `invalid_query`. The browser quick switcher (`Cmd/Ctrl+K`) offers workspace message search, groups matching rows by conversation with literal match highlighting, and navigates via `/app/w/:workspaceId/c/:conversationId?message=:messageId`. The machine-readable route and DTOs are in [`contracts/im/http_chat.thrift`](../../contracts/im/http_chat.thrift) and [`contracts/im/model.thrift`](../../contracts/im/model.thrift).
- Threads remain a false capability; replies continue to use the existing `replyToId` quote reference and the UI must not offer thread actions. Reactions, read receipts, presence and per-conversation notification levels are specified in their own sections below and are each capability gated. Literal history search is available through the generic history API.

### Conversation mutation retries

`POST /api/v1/workspaces/:id/conversations` and `POST /api/v1/conversations/:id/members` optionally accept `Idempotency-Key` (1–128 ASCII letters, digits, `.`, `_`, `:`, `-`). Keys are scoped to the authenticated caller across these two operations. Chat schema 6 stores only the caller, key, canonical request hash and conversation ID; the receipt, mutation and sync events commit in one Chat-owned transaction. Concurrent identical requests perform the mutation once. A reused key with a different operation, destination or payload returns 409 `idempotency_conflict`. Failed transactions do not consume the key. Ordinary requests without a key preserve their existing semantics. Responses retain the normal endpoint status (201 for creation, 200 for member addition).

Successful retries return current conversation metadata under the same read/management ACL as the original operation, even when new creation is disabled. Retries never recreate a deleted conversation, restore a removed participant or emit duplicate sync events. A caller who has lost the required membership/management permission receives the normal access error. The member list may have changed since the original response; a removed invitee stays removed. A deliberate new membership change requires a new key. Receipts survive database backup/restore and carry no Agent Runtime concepts.

## Mentions and reply attention

- `GET /api/v1/attention?cursor=&limit=50&unreadOnly=true|false` -> `{items:[{message,conversation:{id,workspaceId,name,type},workspaceName,reasons:["mention"|"reply"],isRead}],cursor?,unreadCount,channelUnreadCount,attentionUnreadByConversation:[{conversationId,unreadCount}]}`. The identity always comes from the normal authenticated session/principal, never a requested user or Agent ID. This Chat-owned read projection uses existing messages, current structured mentions, reply references and conversation read cursors; it creates no notification table, service, event type or runtime resource. Humans and authenticated Agent principals use the same rules.
- A non-self message is relevant when it currently mentions the caller by ID or replies to the caller's unretracted original in the same conversation. Reasons deduplicate into one item. Plain `@name` text and self-authored messages do not generate attention. Retracting the reply target removes the reply reason; an independent mention reason can remain. Edits/retractions are evaluated from current message data rather than copied alert bodies. Disabling new mention/file writes preserves readable delivered content.
- Every page and its global `unreadCount`/`channelUnreadCount` recheck current workspace and channel/direct/group membership; neither platform administration nor workspace ownership bypasses private conversation membership. Reads acquire workspace/conversation share locks in sorted order and recheck membership after waits, ordering them with revocations. Removal of a granting owner also removes the delegated principal's normal visibility. No unauthorized workspace name, message snippet or unread count is returned.
- Items sort newest first by immutable `(createdAt,id)`. The optional opaque cursor resumes strictly before that pair, independent of edits and timestamp ties. `limit` is 1–100 and malformed cursors/filters return 400. `unreadCount` counts all currently authorized relevant messages above their conversation's read cursor (`channelUnreadCount` counts the channel subset), independent of pagination and the unread filter. `isRead` uses the same monotonic cursor; there is no separate per-alert acknowledgement.
- `attentionUnreadByConversation` is a complete current projection for every authorized conversation, including zero-count entries. It counts the same mention/reply messages as the inbox, independently of `items`, `cursor`, `limit`, `unreadOnly` and notification preferences. Items, global counts and grouped counts come from one SQL snapshot after the ordinary ACL locks/rechecks. Grouped counts sum to `unreadCount`, and their channel subset sums to `channelUnreadCount`. The new server always returns this field, including an empty array when no conversations are authorized; a legacy response omitting it means unknown, not an authoritative all-zero projection. Clients must not compute it by subtracting one page of items from a global number.
- Browser route `/app/attention` provides all/unread views from one rail entry with an unread badge. Opening/browsing the list never acknowledges messages or merges result bodies into the timeline. Selecting an item builds an ordinary `/app/w/:workspaceId/c/:conversationId?message=:messageId` link, revalidates the source with the existing message/context endpoints and focuses that source. Only after it renders in a visible conversation does the browser explicitly call the existing read API through the target's sequence, leaving later messages unread. A denied, retracted, hidden or abandoned source load is not acknowledged. Returning to latest resumes normal timeline read behavior. The inbox header also offers an explicit "mark all read" action that pages `unreadOnly=true` items (`limit=100`), computes each conversation's highest unread attention `message.seq`, and calls the existing `POST /api/v1/conversations/:id/read` endpoint with bounded concurrency, leaving later non-attention messages unread.
- Account/ACL-scoped query keys, abort signals and local source reconciliation discard stale responses after navigation/account/permission changes. Existing durable message, membership and `read.updated` sync events refresh list/count queries, including other devices' acknowledgements. Content changes also invalidate an in-flight initial count request: an edit or retraction can change relevance without advancing `lastSeq` or `readSeq`. Only a result for the current account, access/read scope and content revision may publish its complete count map. Offline clients retain the last confirmed projection as stale rather than deriving counts from a partial message cache; revoked conversations are removed immediately.
- The browser may optionally display in-tab system notifications via the Web `Notification` API while the page is open when the user explicitly opts in from account settings (with message body preview off by default for privacy) and a live synced `message.created` event mentions the user, is a direct/group message, or replies to the user's unretracted message while the tab is hidden or viewing another conversation. An uncached reply target may be resolved through the ordinary authorized message endpoint; before displaying the notification the client rechecks current access, message/read state and notification preferences. Initial history sync does not generate notifications. No browser push, service worker, email or external provider call is involved. The schema vector and deployment configuration are unchanged. The machine-readable route and DTOs are in [`contracts/im/http_chat.thrift`](../../contracts/im/http_chat.thrift) and [`contracts/im/model.thrift`](../../contracts/im/model.thrift).

## Reactions

- `PUT /api/v1/conversations/:id/messages/:messageId/reactions/:emoji` -> `{reactions,reactionsVersion}` adds the caller's reaction; `DELETE` on the same route -> `{reactions,reactionsVersion}` removes it. `:emoji` is the percent-encoded emoji. Both are idempotent: repeating an add or removing an absent reaction returns the current list and version. They require current conversation membership and the ordinary cookie CSRF/Origin or authenticated principal checks; humans and Agent principals use the same API and ACLs, and neither workspace ownership nor platform administration bypasses them.
- `emoji` must be exactly one fully-qualified Unicode Emoji 17.0 sequence (skin-tone modifiers, ZWJ sequences, keycaps and flags included), at most 64 UTF-8 bytes. The allowlist is generated offline from the pinned official data; no production network lookup or hand-written Unicode range approximation is used. Custom images, shortcodes, components by themselves and arbitrary text return 400 `invalid_reaction`. A message holds at most 20 distinct emoji; a new emoji beyond that returns 409 `reaction_limit`, while adding the caller to an existing emoji remains allowed. Each participant reacts with a given emoji at most once.
- Message `reactions:[{emoji,count,userIds}]` is ordered by each emoji's first reaction time; `userIds` lists every current reactor in reaction order and `count` equals its length. Omitted or empty means no reactions. The browser derives "reacted by me" from `userIds`, so message payloads stay identical for every reader. A reactor who later loses access remains attributed, like their authored messages.
- `reactionsVersion` is a nonnegative per-message counter encoded as a decimal JSON string. All new complete Message responses, mutation responses and `reaction.updated` events include it; a newly created message starts at `"0"`. Only an effective reaction mutation increments it. Mutation, counter and durable event commit together; the complete list and its version are read from one SQL snapshot. Removing the final reaction preserves the newer counter with an empty list. Message text edits use their own existing ordering and do not increment this counter.
- Retracted messages cannot gain reactions (409 `message_retracted`) and every read, including the immediate retraction response and old sync events, returns them without reactions. Retraction that removes existing reactions increments the counter; retracting an already empty list preserves the counter. Old sync payloads for a now-retracted message use its current empty reaction state/version and message tombstone. Edits keep reactions.
- Each effective change commits one durable `reaction.updated` sync event carrying `conversationId`, `messageId`, `reactionsVersion` and the complete current `reactions` list; no-op repeats create none. Reactions never allocate a message `seq`, change `lastSeq`/`updatedAt`, unread counts or read cursors, and create no attention item or browser notification.
- Browsers merge reaction state independently from message text, by the server counter across history/context reads, API responses and sync events. A smaller version cannot replace a newer one, including a newer empty list; a known retraction remains terminal. Legacy payloads without a counter cannot overwrite a known version. Latest and independently located history windows subscribe to the same reaction state without inserting old context into the latest timeline. Persisted messages, their reaction versions and the sync cursor are saved together; account/access changes clear or prune the same state and discard stale requests.
- Reactions are not new Agent work: Runtime continues to treat only `message.created` as fresh input, so reacting to an Agent message cannot start a turn or a reaction loop. Explicit Agent history/message reads include the ordinary `reactions` field. This change adds no Agent reaction tool.
- `im.reactions.create` gates new reactions. Removing one's own reaction remains allowed when it is off, and persisted reactions stay visible. The browser always shows persisted reaction chips and reactor names under ordinary conversation ACLs, independently of the creation capability. Clicking one's own chip removes that reaction even when creation is disabled. Clicking a chip to which the caller has not reacted may add a reaction only when creation is enabled; otherwise it must not issue a PUT. The emoji picker is available only when creation is enabled.

| `im.reactions.create` | Persisted chips and reactor names | Remove own reaction | Add a reaction / emoji picker |
| --- | --- | --- | --- |
| `true` | Visible under conversation ACLs | Allowed | Allowed |
| `false` | Still visible under conversation ACLs | Still allowed | Disabled / hidden |

## Read receipts

- `GET /api/v1/conversations/:id/read-receipts` -> `{conversationId,eligibleCount,readSeqCounts:[{readSeq,count}],members?:[{userId,readSeq}]}`. Requires current conversation membership; neither workspace ownership nor platform administration bypasses it. It derives entirely from existing per-member read cursors and adds no storage.
- Eligible readers are current members of the conversation other than the caller, humans and Agent principals alike, using each participant's ordinary read cursor. An Agent's cursor means "durably received", not "processed": Runtime advances it through the ordinary `POST /api/v1/conversations/:id/read` API only after the corresponding inputs are persisted in its inbox, independent of turns, tools or replies, so receipts expose no execution detail. A disabled or deleted Agent stops advancing; removed members drop out immediately under the ordinary membership locks.
- `readSeqCounts` aggregates eligible readers by cursor, descending by `readSeq`, without identities; the readers of sequence `s` are the sum of counts with `readSeq >= s`. `members` is present only for `direct` and `group` conversations and names each eligible reader's cursor. Channels never return reader identities.
- The browser shows receipts only on the caller's own unretracted messages: "已读"/"未读" in direct conversations, "N 人已读" with an expandable read/unread name list in groups, and "N 人已读" without names in channels. To limit noise it labels the newest own message persistently and earlier own messages on hover/focus.
- When an eligible member's read cursor advances, Chat publishes an ephemeral hint and Realtime sends WebSocket `{type:"receipts.changed",conversationId}` to current members, coalesced to at most one per conversation per second. Hints may be dropped or duplicated and carry no reader data; clients viewing the conversation refetch, and also refetch on open, focus and reconnect. No durable sync event is created for other members' reads; the caller's own `read.updated` events are unchanged.
- Coalescing retains a trailing invalidation for recipients with updates during the window and rechecks current membership when delivering it. The browser refetches after membership changes, removes revoked reader data, and retries transient failures while the viewed conversation remains eligible. Requests and retry timers are canceled on account/access changes, capability disablement or leaving the conversation; a failed request does not mean every member is unread.
- `im.read_receipts.view` gates the endpoint and hints. When off, the endpoint returns 403 `feature_disabled`, no hints are sent and the UI shows no receipt labels; read cursors and unread behavior are unaffected.

## Presence

- Realtime owns presence in disposable Redis state; no database table, sync event or audit row is created and Redis loss only resets indicators. Presence never controls message access, delivery, notifications or Agent work.
- Only human sessions publish presence. A participant is `online` while at least one of its authenticated WebSocket connections reported recent activity, `away` when it is connected but every connection has been idle or hidden for five minutes, and `offline` 30 seconds after its last connection closes (absorbing reconnects). Connections authenticated as Agent principals are ignored regardless of activity.
- Client WebSocket message `{type:"presence",state:"active"|"idle"}` reports the connection's state; the browser sends `active` on input or when the tab becomes visible and `idle` after five minutes without input or while hidden, at most once per 30 seconds unless the state changes. Unknown fields are rejected.
- `GET /api/v1/workspaces/:id/presence` -> `{presence:[{userId,state:"online"|"away"}]}` lists current human members of that workspace who are not offline; absence means offline. Realtime verifies current workspace membership through Chat RPC; non-members receive 404. No last-seen time, device, client or location is exposed.
- WebSocket `{type:"presence",userId,state:"online"|"away"|"offline"}` is delivered to connections of users who currently share a workspace with that participant, coalesced per participant. It is a hint; clients refetch the workspace snapshot on connect and reconnect.
- Agents have no IM presence. The browser labels Agents "可用" or "已停用" from the public Agent profile's `enabled` field returned by workspace discovery; this is saved owner configuration, explicitly not online or runtime status, and IM services remain unaware of Agent types. Discovery rules are unchanged; an Agent member whose profile is absent from discovery shows no availability label.
- `im.presence.publish` gates publication: when off, Realtime ignores client presence messages, sends no presence hints and returns an empty snapshot, and the UI hides human presence indicators.

## Conversation notification levels

- `notificationLevel` on each Conversation is the caller's own setting: `all` (default), `mentions` or `none`. It is never shown to other participants.
- `PUT /api/v1/conversations/:id/notification-level` body `{level:"all"|"mentions"|"none"}` -> `{conversationId,notificationLevel}`. Requires current membership, the ordinary write authentication and `im.notifications.configure`; repeated identical writes are idempotent. Each effective change commits a durable `preference.updated` event in the caller's own sync stream only, carrying `conversationId` and `notificationLevel`, so other devices converge. The preference is deleted when the caller loses access to the conversation; regaining access starts from `all`.
- The level is browser presentation only. It never changes message access, history, read cursors, the `/api/v1/attention` projection or counts, Agent runtime input, or what other participants see.
- Browser unread model: "relevant" means a direct or group message, or a message that mentions or replies to the caller. Under `all`, direct/group conversations show a count badge, channels with unread messages are bold without a count, and channels with relevant unread messages show an `@` badge with that count. Under `mentions`, only relevant messages produce badges; other unread activity is not bold. Under `none`, the conversation is dimmed with a mute icon and shows no badge or bold. The sidebar, document title counts, workspace dots and in-tab browser notifications all use this one selector. The rail inbox badge and `/app/attention` keep the attention API's counts regardless of level.
- Ordinary unread remains `U=max(lastSeq-readSeq,0)`; attention unread `A` comes from the complete per-conversation projection. Direct/group use `U` for both `all` and `mentions`, with a plain number; channel badges use `@ A` in both modes. Only `all` channels use ordinary `U` for bold/dot. The title sums unmuted direct/group `U` and unmuted channel `A`, without double-counting direct/group attention. When the sum is zero, an `all` channel's ordinary unread may show a title dot. Desktop candidates are ordinary direct/group messages or relevant channel messages; `all` does not broaden channel desktop alerts to every ordinary message.
- When `im.notifications.configure` is off, persisted levels are still returned and honored; only changes are rejected with 403 `feature_disabled`.
- Chat schema 7 adds reaction storage, a default-zero per-message reaction counter and each member's notification-level preference. Existing message bodies, sequence numbers, attachments, receipts and annotations are preserved. Read receipts, attention counts and presence add no schema.

## Conversation files

- Descriptor: `{id,filename,mediaType,sizeBytes,sha256}`. Metadata is plain untrusted text. No public/signed URL, binary or base64 is included in message, history, bootstrap or sync payloads. `mediaType` is server-sniffed; it is descriptive, never permission to render or execute inline.
- Bootstrap additionally returns `attachmentLimits:{maxFileBytes:4194304,maxFilesPerMessage:8}`. The independent IM constants in `pkg/imlimits` also bound Agent downloads and Sandbox imports. One file contains 1 byte through 4 MiB. A message may contain 8 files. The browser queues multiple uploads, exposes pending/remove/retry/error states and supports file-only messages.
- `POST /api/v1/conversations/:id/attachments` accepts `multipart/form-data` with exactly one `file` field -> 201 `{attachment:Descriptor}`. Requires current conversation membership and enabled `im.attachments.upload`, with ordinary cookie CSRF/Origin or authenticated principal checks. Filename is 1–180 Unicode characters (512 UTF-8 bytes maximum), without path separators, control/format characters, or leading/trailing whitespace. Client MIME declarations are ignored. Empty/oversized files return 413 `attachment_too_large`, invalid filename/parts return 400, and saturated transfers return retryable 429 `attachment_busy`.
- Uploads optionally accept `Idempotency-Key` (1–128 ASCII letters, digits, `.`, `_`, `:`, `-`). The key belongs to the authenticated uploader across conversations. The first successful request returns 201; an identical retry returns 200 and the same descriptor, including after linkage or disabling new uploads. A changed destination, filename or file hash returns 409 `upload_conflict`. Concurrent retries create one upload. Expiry, pending deletion and message retraction preserve a byte-free receipt and return 410 `attachment_upload_unavailable`; the key never creates another file. Ordinary uploads without a key retain their existing behavior.
- `GET /api/v1/conversations/:id/attachment-uploads/:uploadKey` -> `{attachment:Descriptor}` recovers the caller's own successful upload after a lost response without retransmitting or re-reading a source file. It rechecks current ordinary conversation access, stays available when new uploads are disabled, and exposes no other uploader's receipts or file bytes. An authorized unknown key returns 404 `attachment_upload_not_found`; a removed/expired upload returns 410. Current membership denial keeps the ordinary 404 behavior.
- Each unlinked upload is private to its uploader, confined to that conversation and expires after 24 hours. A sender can retain at most 32 pending files across conversations; admission is atomic. Hourly Chat-owned cleanup runs even when upload writes are disabled. Upload also clears that sender's expired pending files. A lost upload response may leave a private pending file until cleanup; the client may retry the upload, with no duplicate IM message side effect.
- `DELETE /api/v1/conversations/:id/attachments/:attachmentId` -> 204 removes only the caller's unlinked file. It is idempotent for absent files, requires normal write authentication/current membership, and remains usable when upload admission is disabled. Linked or someone else's files return 404.
- The message transaction associates every `attachmentId` atomically. Files must be unexpired, unlinked uploads by the sender in the same conversation. Invalid, foreign, repeated, consumed or expired IDs reject the whole send without allocating a sequence/event or consuming any upload. A file cannot be linked to another message. The original attachment IDs are retained for message retry comparisons after edits/retraction.
- `GET /api/v1/conversations/:id/attachments/:attachmentId/content` returns authorized bytes. Before linkage only the uploader can download. After linkage current ordinary conversation members can download; workspace ownership/platform administration never bypasses the ACL. A removed member, wrong conversation, expired pending file, retracted message or unknown file returns 404. Revocation is ordered with reads using the same membership locks; an already authorized in-flight transfer can finish. Retraction removes stored binary bytes in the message transaction. It cannot remove a copy a participant has already downloaded.
- Downloads use `application/octet-stream`, forced `Content-Disposition: attachment`, `nosniff`, a restrictive sandbox CSP and `Cache-Control: no-store`. The browser uses an authenticated same-origin request and a temporary Blob URL; it never trusts a file-supplied URL or HTML. Reads and persisted descriptors remain available when upload writes are disabled.
- Chat schema 3 owns both metadata and bounded PostgreSQL `bytea`. History queries select only the message JSON descriptors, never binary content. Two process-wide transfer slots and streaming Hertz multipart admission bound binary buffers under Chat's configured memory budget. Existing Chat database dumps include all attachment bytes and relationships; no new storage service, host volume or deployment environment is introduced. The disposable restore check verifies a linked non-UTF-8 binary attachment, descriptor and original IDs.
- Chat schema 4 adds generic upload receipts without changing existing attachments/messages. Receipts retain only uploader, key, conversation, request fingerprint and an optional attachment relationship, not binary content, runtime IDs, Sandbox paths or model configuration. They are included in the Chat-owned backup and survive deletion of the referenced attachment.

The machine-readable routes and DTOs are in [`contracts/im/http_chat.thrift`](../../contracts/im/http_chat.thrift) and [`contracts/im/model.thrift`](../../contracts/im/model.thrift).

## Durable sync and WebSocket

- `GET /api/v1/sync?cursor=<opaque-or-decimal>&limit=100` -> `{events,cursor,hasMore}`. Empty/0 cursor starts the user's durable event stream. Stream is per-user; membership is rechecked before returning protected payloads. Cursor must advance past filtered events as well. Invalid/future cursor returns a defined error rather than silently skipping data.
- Event: `{id,type,conversationId?,workspaceId?,message?,conversation?,readSeq?,messageId?,reactions?,reactionsVersion?,notificationLevel?,createdAt}`. `id` is the durable sync cursor. Types: `message.created`, `message.updated`, `message.retracted`, `reaction.updated`, `conversation.created`, `membership.changed`, `read.updated`, `preference.updated`. A membership removal may invalidate cached entities; clients clear/refetch bootstrap. Consumers ignore event types they do not handle.
- `GET /api/v1/ws` upgrades to WebSocket. Server emits JSON `{type:"ready"}` then `{type:"sync.required"}` as a hint. Clients use HTTP sync as the durable truth; hints can duplicate/coalesce and are never the only message payload. Reconnect always runs HTTP sync from the last applied cursor. Backoff with jitter, heartbeat and bounded write buffers.
- Client ephemeral messages `{type:"typing",conversationId,isTyping:true|false}`; server messages `{type:"typing",conversationId,userId,displayName,isTyping:true|false}` when supported. Typing uses the ordinary authenticated participant's current display name; it exposes no execution details. A positive hint expires five seconds after receipt unless refreshed; clients remove expired entries on their one-second cleanup tick. Stop hints clear immediately. Presence (client `{type:"presence",state}`, server `{type:"presence",userId,state}`) and read-receipt hints (`{type:"receipts.changed",conversationId}`) are defined in [presence](#presence) and [read receipts](#read-receipts); they are capability gated and never control message access.
- `POST /api/v1/conversations/:id/typing` body `{isTyping:boolean}` -> 204 is the equivalent generic HTTP signal, owned by Realtime. It accepts the normal human cookie/Origin/CSRF flow or an authenticated service principal bearer token plus service key, with the existing prohibition on browser bearer impersonation. The server derives sender ID/name, checks current conversation membership and `im.typing.publish` in both Realtime and Chat, and rechecks sender/recipient membership before delivery. Unknown fields, including sender IDs and runtime metadata, are rejected. Repeated positive hints are coalesced within 300ms per participant/conversation; stop hints are never throttled and a successful stop allows an immediate fresh start. Signals for a participant/conversation are published serially, so an earlier in-flight start cannot overtake a successfully published stop.
- Typing is ephemeral: no message, sync event, audit row, Session or activity resource is created. Redis loss may drop hints; failed clears or a publisher crash converge through the same five-second client TTL. Turning the write flag off rejects new signals, and existing ephemeral hints expire normally.
- Session revocation must disconnect or cause periodic revalidation; every protected sync/read/write must revalidate current identity/membership.

## Feature capabilities

`capabilities` is a map of booleans: `auth.public_signup`, `auth.password_reset`, `im.dm.create`, `im.group.create`, `im.channel.create`, `im.message.edit`, `im.message.retract`, `im.typing.publish`, `im.presence.publish`, `im.attachments.upload`, `im.reactions.create`, `im.threads.create`, `im.read_receipts.view`, `im.notifications.configure`. Capability=true requires both implemented functionality and an enabled backend flag plus user permission. Persisted data is still returned if its write flag is turned off. `im.threads.create` remains false.

## Operational contract

Identity: HTTP `:8081`, Kitex RPC `:8881`; Chat: HTTP `:8082`, Kitex RPC `:8882`; Realtime: HTTP/WS `:8083`. Each exposes `/healthz` (liveness), `/readyz` (dependencies), `/version` with build SHA/version. Use env `HTTP_ADDR`, `RPC_ADDR`, `IDENTITY_RPC_ADDR`, `CHAT_RPC_ADDR`, `DATABASE_URL`, `REDIS_ADDR`, `APP_ORIGIN`, `COOKIE_SECURE`, `BOOTSTRAP_INVITE_CODE` (optional, default `teamie-bootstrap`), `FEATURE_FLAGS_FILE`. `REGISTRATION_CODE` is removed from the new pre-release design. Runtime secrets may use env backed by protected host config; never bake them into images. Each service applies its own embedded, forward-only idempotent migrations before readiness. Release scripts serialize migration and rollout.

Caddy routes `/api/v1/auth/*` to Identity, `/api/v1/ws`, `/api/v1/conversations/*/typing` and `/api/v1/workspaces/*/presence` to Realtime, other `/api/*` to Chat, and remaining requests to the static web container. Frontend uses same-origin relative URLs. Build context for backend Dockerfile is repository root, build arg `SERVICE=identity|chat|realtime`; executable packages are `./services/<service>/cmd`. Web build context is repository root, Dockerfile `apps/web/Dockerfile`.

Edge configuration requires `SITE_ADDRESS` equal to `APP_ORIGIN` and `TLS_SERVER_NAME` equal to that origin's hostname (without scheme/port). The latter configures Caddy `default_sni` for IP clients that omit SNI. It does not change the browser Origin or authorize another hostname.
