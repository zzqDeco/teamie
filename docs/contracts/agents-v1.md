# Agent API and execution contract — v0.3.8

This contract extends the independent IM product. IM services do not depend on Eino, model configuration, runtime sessions, or sandbox state. Services use independent Go modules under `services/`, separate PostgreSQL databases/roles, container images and authenticated Thrift IDL contracts in [`contracts/agent/`](../../contracts/agent) (`model.thrift`, `http_control.thrift`, `http_gateway.thrift`, `rpc_control.thrift`, `rpc_runtime.thrift`, `rpc_gateway.thrift`, `rpc_sandbox.thrift`).

## Product decisions

- A human creates and owns each Agent. Agent ID equals its independent IM participant ID. Ownership does not confer access to other participants' conversations.
- Owner settings are name, description, selected workspace IDs, and enabled state. No user-supplied model, provider, key, prompt, tool, or budget controls in this release.
- Agent working context is private across its authorized conversations. A human owner manages the basic profile, workspace visibility and enabled state only. Ownership and platform administration do not grant browser access to Session, run, task, tool, error or activity details.
- Selected teams are workspace-level visibility. Only workspaces where the owner is currently a member may be selected. Agents use ordinary workspace/conversation membership and IM ACLs. Removing the granting owner revokes delegated memberships. Moderator removals must not be undone by background reconciliation.
- One durable Session per Agent (`agent:<id>`) intentionally carries working memory across its authorized conversations. Session compaction preserves provenance and original message references. IM history is never deleted by compaction.
- Newly committed message bodies, sender identity, workspace/conversation/message/event IDs and an optional parent `replyToId` enter the runtime inbox promptly. Self-authored messages are not new work. Each Agent has one Session writer and one serial native TurnLoop. Worker/Attempt/lease/fence are private implementation details; they do not add architecture services or owner settings. Fresh input delivery is independent of the current run batch.
- Distant history is read through explicit IM tools. Every chat write is an explicit tool invocation with an explicit destination. Ordinary model output and operational errors are never automatically published to IM.
- Platform administrators configure the shared OpenAI-compatible model gateway. A healthy but unconfigured gateway produces `model_unconfigured`; Agents wait without losing their inbox. Releases preserve the administrator's saved gateway configuration and credentials.
- Tools and Sandbox are platform presets. Execution children have no provider/IM credentials, host Docker socket, network, or arbitrary host mounts. Workspace lifetime and execution-container lifetime are independent.

## Owner and discovery HTTP

All endpoints require a human cookie session. Writes require the existing CSRF and trusted Origin checks. Agent bearer credentials cannot manage definitions. Platform admin is not an ownership bypass.

Public `Agent` JSON has exactly `{id,principalId,ownerId,ownerName,name,description,workspaceIds,enabled,createdAt,updatedAt}`. `principalId=id`. A separate public DTO projects these fields for every create, update, read, list and discovery response. No runtime state, Session ID, activity timestamp, error, revision, tombstone or other internal metadata is returned. `enabled` is the owner's saved configuration; it does not assert online status or model/provider health. Internal configuration revisions still fence runtime changes; there is no public revision/If-Match contract.

- `GET /api/v1/agents` -> `{agents:[Agent]}` owned by caller.
- `POST /api/v1/agents` body `{name,description?,workspaceIds,enabled?}` -> 201 `{agent}`. Empty workspace IDs are allowed; the Agent has no team membership until a team is selected.
- `GET /api/v1/agents/:id` -> `{agent}` owner only.
- `PATCH /api/v1/agents/:id` accepts optional `name`, `description`, `workspaceIds`, `enabled` -> `{agent}` owner only. Profile/visibility changes fence old configuration revisions. Disable revokes IM credentials and stops active work.
- `DELETE /api/v1/agents/:id` -> 204 owner only. Tombstone definition, revoke credentials/membership and cancel work; preserve attributable IM message history. Deleted profiles return 404 on public reads and are excluded from listings/discovery.
- `GET /api/v1/workspaces/:id/agents` -> `{agents:[Agent]}` discovery only for current members, selected visibility and actual Agent membership. Each profile's `workspaceIds` contains only the requested workspace ID, including when the caller is the owner. Other selected workspaces remain private. The owned profile endpoints retain the owner's full selected list.

Public capabilities: `agents.enabled`, `agents.create`, `agents.update`, `agents.delete`, `agents.discover`. Existing `im.dm.create` and `im.group.create` govern conversations. Disabled write features preserve persisted profiles/history. Personal Agent profile management uses `/app/agents` and `/app/agents/:id`, reached from the Agent button immediately above the account avatar at the bottom of the leftmost workspace rail. The avatar menu contains account settings and sign out. The workspace member directory at `/app/w/:workspaceId/members` lists humans and visible Agents together with an Agent badge and uses the ordinary IM conversation/member APIs. The sidebar has no standalone member-directory entry; conversation headers still open the current conversation member list and its invitation action. The workspace title is plain text; its adjacent plus opens capability-gated direct and group creation. Workspace switching and creation use the workspace rail. `/app/w/:workspaceId/agents` redirects to this directory. Turning discovery off preserves persisted Agent members and conversations, but does not admit new Agent selections. The account settings page exposes platform management only to human platform administrators; administrator pages are absent from the main navigation.

## Administrator model gateway HTTP

Gateway owns encrypted provider secrets and configuration in its own database. Only `platformRole=admin` human sessions may access these APIs. Private key bytes must never appear in reads, logs, frontend caches, URLs, or Sandbox requests.

- `GET /api/v1/admin/model-gateway` -> `{config:{baseUrl,model,hasApiKey,enabled,configured,contextWindowTokens,updatedAt,webSearch:{provider,hasApiKey,enabled,configured}},status:"unconfigured"|"ready"|"disabled"}`. `ready` describes saved configuration, not observed upstream health.
- `PUT /api/v1/admin/model-gateway` body `{baseUrl,model,apiKey?,enabled,clearApiKey?,contextWindowTokens?,webSearchEnabled?,webSearchApiKey?,clearWebSearchApiKey?}` -> same redacted response. Omitted `apiKey` or `webSearchApiKey` preserves the stored key; omitted `webSearchEnabled` preserves the stored web-search enabled state. `clearApiKey` and `clearWebSearchApiKey` explicitly remove their respective keys and cannot accompany a new key.
- `POST /api/v1/admin/model-gateway/test` -> `{ok,model,latencyMs}`. Test saved configuration using one small real model request; the UI labels this effect. CI uses a disposable protocol fixture; production uses only administrator-supplied credentials.

`contextWindowTokens` defaults to 16384, accepts 4096–2000000 and is preserved when omitted. It is an administrator declaration for bounded runtime summarization, not a capability probe. Gateway schema 3 adds `web_search_encrypted_key` and `web_search_enabled` to `gateway_config` for platform-managed Tavily Search and Extract credentials. Frontend route `/app/admin/gateway`; existing invitation admin route is preserved. Service readiness is independent of whether a model or web search provider is configured.

## Runtime durability and tools

The runtime owns inbox cursor, pending inputs, worker leases/fencing, run state, Eino Session events, checkpoints, compaction state and tool receipts. IM sync is the durable input source; WS/Redis only accelerate wakeups. Persist events before advancing the source cursor, deduplicate source events, revalidate membership when processing delayed inputs, and keep recovery isolated from configuration revisions.

Preset tools: list authorized conversations, query/paginate IM history, fetch a referenced message or sequence context, explicitly send/reply, native filesystem/PlanTask tools, recoverable workspace execution, and native task progress/control tools. Each result is a runtime observation, not an automatic chat post. Send intent and stable `clientMessageId` survive retries; output is acknowledged only after IM persistence. Tool-call recovery must not duplicate already committed sends or unknown external side effects. Gateway calls and cancellation use a distinct execution-attempt ID. Sandbox preserves durable run/request IDs for receipt replay and carries a separate optional executionId for cancellation, so stopping one attempt cannot poison its later retry.

### Explicit IM file import

Fresh inputs and explicit history/message reads include only `attachments:[{id,filename,mediaType,sizeBytes,sha256}]` descriptors. File-only messages are durable new inputs. No binary, base64, automatic URL fetch, file parsing or IM send occurs during inbox ingestion or prompt construction. Structured message/source IDs continue to identify the original audience. A file name and its contents remain untrusted data.

`im_get_attachment({conversationId,messageId,attachmentId,path})` explicitly downloads a known file from a known source message into the calling Agent's Sandbox. It first reads that message under the Agent's current ordinary IM identity, confirms the descriptor, then downloads through Chat's authenticated content endpoint under the same current ACL. Foreign/unlinked/retracted/removed-access files remain unavailable. No arbitrary external URL or host path is accepted. A real byte-length/SHA-256 check precedes import. The tool returns a path, byte count and hash; file content never appears in the JSON tool observation. Legacy native text reads retain their 256 KiB UTF-8 ceiling. New-policy `workspace_read_page` supports explicit byte pages through larger allowed text files; binary processing remains an explicit Sandbox execution step.

Internal `SandboxService.ImportFile(SandboxImportRequest)` carries a Thrift `binary` field, Agent/run/stable request ID, confined path and SHA-256. It uses the runtime service credential only in the supervisor RPC; execution children receive no IM/service/provider credentials or network. The runtime rechecks configuration authorization and the worker lease immediately before import. A retry reuses the logical run/tool-call identity, independent of execution attempt. Sandbox stores a private intent before atomic no-replace publication and a completion receipt afterwards. It reconciles a lost result only when the exact expected bytes exist; ambiguous intervening changes return `execution_unknown`. Receipt replay preserves later file edits and never overwrites another existing file. Agent workspaces and trusted receipts are physically separate; traversal, target/parent symlinks and outside-root paths are rejected.

The shared IM file limit is 4 MiB, fitting under the existing execution child's 8 MiB `fsize` limit. Import/text mutation admission also accounts for the Agent workspace's 64 MiB/4096-entry budget; supervisor monitoring cancels execution that crosses the observed budget. This is admission plus sampled monitoring, not a kernel hard aggregate filesystem quota. Existing child memory/CPU/PID/output/network restrictions remain enforced. Sandbox RPC bounds framed payload size to the file ceiling plus a small metadata allowance. Chat schema advances to 3; Runtime/Gateway/Control/Identity schema versions do not change for files. Existing PostgreSQL backup/restore includes IM files; durable Sandbox files/receipts remain in the existing protected Sandbox roots.

### Structured recipient annotations

IM messages/history may carry ordinary `mentions:[{userId,start,end}]` metadata, using UTF-16 text ranges. Runtime persists it with the real source envelope and passes it to the continuous Session; unmentioned new messages are still ingested. Mention IDs identify recipients only, never sender roles, membership, authority or a permission to share another conversation. Source references and compaction continue to retain the actual request/conversation/message identity.

The private `agents.mentions.v1` flag admits new context-v1 Runs to the mention-aware send tool and guidance. Its immutable budget snapshot records `structuredMentions:true`; existing Runs retain their previous prompts, tool schemas and request hashes. New Runs can explicitly pass `mentions` to `im_send_message`, combined with files when file delivery is admitted. IM applies the same membership validation to human and Agent senders. Chat schema advances to 5; Runtime remains 3. This remains unreleased product code and adds no owner settings or browser runtime resources.

### Explicit file-result tools

The private `agents.files.deliver.v1` admission flag selects file-result tools only for newly admitted context-v1 Runs. The immutable context budget snapshot stores this selection; retries and native checkpoints keep it even if live flags change. Existing snapshots omit the field and retain their exact tool manifests, prompts and hashes. This adds no browser runtime capability, owner setting or execution architecture layer.

`im_upload_file({conversationId,path,filename?})` explicitly exports one regular file from this Agent's Sandbox (1 byte–4 MiB) and uploads it using ordinary current IM principal credentials. No host path, URL, file bytes, base64 or service credentials enter the model observation. The return value contains only the destination and the normal attachment descriptor. A completed background result uses its recorded source conversation; the tool does not guess an audience or automatically send a message.

`im_send_message` in these newly admitted Runs additionally accepts `attachmentIds`. It explicitly publishes text, files or both under ordinary IM ACLs, attachment ownership and stable message-send identity. Existing Runs retain the former text-only schema. Browser messages reuse the standard attachment cards and authenticated downloads; no Sandbox path, execution/task ID or private runtime result appears in their payload.

Upload identity derives from the durable Run/tool-call identity. Before reading the file, Runtime looks up that upload through IM. A committed upload survives a lost response, file edits/deletion and worker restart; retries reuse its descriptor and never re-export it. If no upload committed, export is an ordinary bounded read and can observe the current file. Runtime verifies length and SHA-256 before transfer and rechecks its worker fence/configuration and authenticated workspace source closure before publishing. A conflicting key or removed/expired upload fails explicitly, without silently changing bytes or reusing a spent attachment in a new message.

Private `SandboxService.ExportFile` carries bounded binary data and SHA-256 only between supervisor and Runtime. It rejects outside-root paths, parent/target symlinks, non-regular files and observable concurrent file changes. Export executes no child or network operation and adds no inference duration budget. IM remains unaware of Sandbox/Agent runtime types. Chat schema 4 owns the generic upload ledger; Runtime schema remains 3.

Native summarization stores a bounded source-aware summary plus recent coherent message/tool-call groups. Its model request explicitly forbids tool calls (`tool_choice=none`) and asks for plain summary text; empty or tool-bearing summaries remain invalid and cannot execute IM tools. Ordinary Agent turns retain their tool access. Summary requests fit the configured context window and transport limit. Long-term Session persistence and interrupted execution checkpoints are separate. Compatible native checkpoints use Resume; recovery retains model/tool receipts and the run's pinned Session view. A model configuration error leaves durable inputs available for retry after configuration.

Native Eino background TaskStore, TaskEventStore, NotificationOutbox and writer protocols are implemented in PostgreSQL. A stable logical task ID survives replay. Manager/executor activity and Sandbox execution do not write the Session in parallel; durable completion notifications return through its input queue. The foreground model slot is released during task waits. Async shell has no default command lifetime limit; request transport deadlines do not determine command lifetime. Ordinary gateway streams preserve upstream content/tool deltas and usage, with distinct explicit HTTP, in-stream, interruption and cancellation outcomes.

Relevant new human input from an active source conversation uses native `AfterToolCalls` preemption. The model-produced tool round, including file mutation and tool-result receipts, completes before the next serial turn consumes the new input. File reads/writes remain ordinary foreground tools; command execution uses durable background tasks. Explicit cancellation and authority/lease revocation retain their separate cancellation paths.

While the serial TurnLoop handles validated new IM inputs, Runtime publishes the ordinary IM typing signal for those input conversations through the generic Realtime HTTP API. It starts only after acquiring the host's foreground slot; the initial slot queue, idle Session, distant history and background-only task notifications do not advertise activity. The signal remains active during tools within that turn and refreshes every 1.5 seconds after rechecking the current Agent configuration, cancellation and fenced worker lease; each HTTP publication also rechecks ordinary IM ACLs. No global Session-busy broadcast is inferred for other conversations.

Turn completion, error, preemption, cancellation, lease loss or configuration invalidation stops the refresh and attempts `isTyping=false`. Refreshes and final clears are serialized and joined before another turn's signal starts. Transport failures never fail the turn; refresh/cleanup requests are bounded to one second, and a crash, disabled flag or revoked credential falls back to the existing five-second browser TTL. `IM_REALTIME_URL` defaults to private `http://realtime:8083`; no host port or new deployment environment is added. Browser hints contain only the normal public participant name/ID and conversation typing boolean. Public Agent profiles retain their exact ten-field contract; no Session, run, task, tool, error or activity endpoint is exposed.

Agent execution uses `NewTypedChatModelAgent[*schema.AgenticMessage]`, a native Agentic Session/TurnLoop and typed summarization/filesystem/task middleware. Tool manifests bind per request through `model.WithTools`; `WithAgenticToolChoice` preserves forbidden, automatic, required and named function choices. Summaries explicitly forbid tool calls. Existing classic Session events remain readable without changing their event IDs, message IDs, source references or stored hashes. Incompatible classic opaque checkpoints are not resumed: the same durable run/input replays verified model/tool/task receipts. A classic model receipt is accepted only when the byte-exact former request hash matches; altered inputs fail with `replay_conflict`. The v0.3.6 format cutover did not change SQL schema or receipt/IM send identity; the versioned context policy below separately introduces Runtime schema 3.

Recovery derives a private tool profile from the same Run's committed model receipts. A Run with classic receipts retains the four pre-attachment IM tools and its original summary provenance representation, including after it appends native receipts and restarts. Fresh Runs retain the attachment tool and current summary representation. Checkpoints must match that profile. Tool results preserve durable output bytes; compatibility with a prior serialized tool result is confined to the same Run's recorded execution and completed receipt, and the entire model request must still match its stored hash. No tool subset search, request-hash rewrite or implicit repeat send is permitted. Terminal failed Runs are not automatically requeued by this patch; an explicit internal retry keeps the original Run, inputs and receipts.

## Versioned private context policy

`agents.context.v1` explicitly admits new logical Runs to `teamie-context-v038`. Runtime schema 3 freezes each Run's context profile and capacity snapshot. Existing Runs retain the v0.3.7 prompt, tools, model hashes and summary policy across retries; live flag or gateway-window changes never rewrite their receipts. Native checkpoints must match the frozen policy and budget hash. This private flag is not a browser capability.

Newly admitted context-policy Runs also freeze `eventDrivenInputs:true` in that snapshot. Runtime already receives and persists new message envelopes and delivers them to the serial TurnLoop; the selected model guidance forbids proactive history/conversation refreshes before, during or after current work. Targeted historical reads remain available for a concrete missing fact/source, explicit original verification or evidence of a relevant change, under unchanged ACLs. Main instructions, history tool descriptions and both summary instructions use the same selection. Earlier snapshots omit it and retain byte-exact prompts, tool manifests, canonical budgets, model hashes and compatible native checkpoints. Runtime migration 9 changes only the ledger and existing writer guard to reject older strict readers; the release schema vector also blocks explicit image rollback and automatic restoration of incompatible old writers. Snapshot capacity version 6, Runtime sync polling and current access checks are unchanged. No table rewrite, browser field, duration budget or tool-call limit is introduced.

Budget snapshot version 2 introduced recovery capacity, reserving output recovery capacity inside the declared context window. Native model validation rejects incomplete function JSON and output-exhausted responses before tool dispatch, then retries within that frozen reserve. Rejected responses remain immutable model receipts and replay uses the same verdict; exhaustion is a private execution failure, never a successful turn or an automatic IM message. Version 1 snapshots keep their original behavior. Runtime migration 4 records the new durable format and fences older binaries; it does not rewrite existing Runs or receipts. Its historical schema vector was Identity 3, Chat 5, Control 1, Runtime 4, Gateway 2. Owner controls, gateway configuration and execution lifetime remain unchanged.

Snapshot version 3 and Runtime migration 5 introduced current-input retention. Full current source bodies and their identifiers stay visible to the main model under capacity pressure; earlier summaries and tool rounds are reduced first. Model-visible historical notices carry immutable refs, while complete source closure remains in private metadata. An oversized current body fails explicitly instead of becoming a metadata-only preview that can be confused with an older task. Earlier Run policies and receipts remain unchanged. Snapshot version 4 and Runtime migration 6 later introduced prefix coalescing. Individually small historical fragments are coalesced into an immutable source-scoped archive before recent complete tool rounds are offloaded. The two newest units remain available whenever hard capacity permits. Committed empty retrievals retain the original request sources without inventing a quoted-data parent; uncommitted or modified observations stay rejected. Versions 1, 2 and 3 retain their original replay behavior, and migration never rewrites their receipts. Its historical vector was Identity 3, Chat 5, Control 1, Runtime 6, Gateway 2.

The new native pipeline offloads large tool results, archives a safe transcript projection, summarizes only an older prefix, and retains complete recent tool rounds plus the latest actual request. It validates both token estimates and transport bytes before dispatch. Private `context_search` and `context_read` expose only immutable observations in the Run's fixed Session view with current source ACL checks, including cached replay. They exclude reasoning/signatures/provider metadata and use UTF-8 byte pagination. Archive state remains in Runtime's database, outside child workspaces; no browser runtime route is added. See [context engineering](../architecture/context-engineering.md) for the source, visibility and recovery contract.

New-policy workspace pages expose continuation/version/coverage; trusted command output persists separately from the small model preview. Source-scoped background notifications include the actual parent Run and source set, without choosing a conversation. A sanitized pre-output model-context rejection is a durable model-step decision before native compaction/retry; partial streaming remains a distinct failure. This preserves one serial TurnLoop and does not impose an inference duration.

The context-engineering baseline targets schema vector Identity 3, Chat 3, Control 1, Runtime 3, Gateway 2. File delivery advances Chat to 4; structured mentions advance it to 5. These are unreleased rollout requirements, not evidence of a published release or deployment. When releasing, create a fresh permanent archive and preserve all previous archives, accounts, conversations, files, runtime receipts and saved gateway settings. Quiesce the old Runtime writer before migration and verify the actual five-database restore, ACR digests, runtime flags, health and external access. Incompatible image rollback is rejected; corrections ship forward.

## Release acceptance

Required public acceptance: exact profile-field allowlist, owner isolation, workspace-scoped discovery without other team IDs, membership revocation, 404 for all retired runtime routes with no runtime RPC access, non-impersonation, redacted admin gateway settings, unchanged invitation/IM flows and desktop/mobile interaction. Private runtime Go integration tests separately cover the continuous Session, arrival of fresh input during an active turn, native checkpoint resumption, source-aware summarization, send deduplication, lease exclusion, native task-store conformance, durable completion wakeup, known Sandbox recovery, cancellation/retry and incremental streaming with partial-failure classification. Public acceptance must not infer these private execution properties from profile metadata. Real provider acceptance remains pending until administrator configuration and authorization; protocol fixtures must be identified as verification infrastructure.

Release from exact checked `main` using the fresh permanent archive specified above. Preserve all previous release branches/tags, including the failed `release/v0.3.1` archive. Behavior-prompt changes still require the quiescent-writer precondition in [behavior guidance](../product/agent-behavior.md). New ACR image digests, runtime flag identity and execution runner image belong in the release manifest. Cross-schema image rollback is rejected; take and verify a pre-upgrade backup.

Snapshot version 5 and Runtime migration 7 introduced reducible task notifications. Complete current IM message bodies remain protected. Batched managed-task notifications are durable machine observations that may be summarized/archived with their exact source closure; their repeated envelopes cannot pin the entire model window. Task data remains available through private history/task tools. Versions 1–4 keep their frozen behavior and receipts. Its historical vector was Identity 3, Chat 5, Control 1, Runtime 7, Gateway 2.

Current admission uses snapshot version 7 (`teamie-visible-bytes-div4-v1`), introduced with Runtime migration 10, building on version 6's long-context capacity from migration 8. The configured gateway window is still an administrator declaration, not automatic model discovery. Version 7 (like version 6) reserves up to 131072 output tokens within that window, permits a 16 MiB native request, and scales recent history, tool-result previews and summary capacity with the window. At a declared 1000000-token window the input limit is 868672 tokens, proactive reduction starts at 781804 (90% of input limit; 651504 in frozen version 6), recent-history target is 262144 and summary output is at most 8192. Version 7 estimates local tokens from provider-visible UTF-8 bytes (`ceil(visible_bytes / 4) + 64`) and calibrates main-context input tokens from the latest intact main-model `ResponseMeta.Usage.PromptTokens` anchor plus the incremental local delta; prefix rewrites invalidate the anchor and summary sub-requests are isolated. Requests include full system policy and tool schemas in admission. A normal first generation allows 32768 output tokens at this window; an incomplete response can recover within the frozen 131072 reserve. This is capacity admission, never an execution-duration limit.

Private runtime/gateway transport supports 65536 input messages, 8 MiB native responses, 128 MiB provider SSE and 256 MiB private NDJSON (including per-chunk framing overhead). Stream aggregation folds bounded batches without dropping native reasoning/tool blocks, usage or cancellation. IM message/file limits, browser APIs, Sandbox isolation and the single global foreground model slot are unchanged. Versions 1–6 retain their exact budget values, counters, request caps, encoding and receipts; changing the gateway window affects only new logical Runs. Schema 10 fences earlier writers, and dump/restore covers all seven capacity versions plus the event-driven selection.

The private `agents.web.v1` flag admits new context-v1 Runs to `web_search` and `web_fetch` by freezing `webSearch:true` in the immutable context budget snapshot. Runtime schema 11 and Gateway schema 3 record this rollout without rewriting existing Runs or receipts. Runtime invokes the gateway over private `POST /internal/v1/web/search` and `POST /internal/v1/web/extract` using `GATEWAY_RUNTIME_TOKEN`; the gateway enforces its own 4-slot web concurrency limit, run-level cancellation (`CancelRun`), strict public HTTP/HTTPS target validation, and calls Tavily Search (`basic` depth) and Tavily Extract (`basic` depth, `markdown` format) using the encrypted administrator key. No local HTML scraping fallback or Sandbox network access is introduced. Both tools record durable receipts in `runtime_tool_calls` and participate in native `ContextPipeline` truncation/clearing and `ContextArchive` (`context_read` / `context_search`) under the Run's source ACLs.

The private `agents.schedule.v1` flag admits new context-v1 Runs to `runtime_clock`, `schedule_create`, `schedule_update`, `schedule_list` and `schedule_cancel` by freezing `scheduledWakeups:true` in the immutable context budget snapshot. Runtime schema 12 adds the private `runtime_schedules` table and raises the writer protocol fence (current schema vector: Identity 3, Chat 5, Control 1, Runtime 12, Gateway 3). Every input envelope (`TEAMIE_NEW_MESSAGE`, `TEAMIE_TASK_NOTIFICATION`, `TEAMIE_SCHEDULE_WAKEUP`) carries a server-authored UTC RFC3339 `createdAt` timestamp, and `runtime_clock` records durable tool receipts so model request hashes remain replay-deterministic without injecting volatile timestamps into the system prompt. When `agents.schedule.v1` and `im.dm.create` are enabled, Runtime also seeds a deterministic cold-start 1-hour recurring heartbeat schedule (`sched-heartbeat-<digest>`, `kind:"interval"`, `intervalSeconds:3600`) scoped to the Agent's authorized workspace `source_refs` once per Agent; if the Agent modifies (`schedule_update`) or cancels (`schedule_cancel`) that heartbeat, Runtime permanently respects the Agent's choice and never recreates or overwrites it. Due schedules are drained under the Agent's worker lease into `runtime_inputs` (`kind:"schedule.wakeup"`, `notification_id:"schedule:<id>:<runCount>"`) with missed-run coalescing for recurring intervals/crons and automatic cancellation when an Agent is disabled, deleted or revised. Schedules inherit causal `source_refs` from the creating/updating Run (or authorized workspaces on cold start) and remain internal runtime state with no browser API exposure.

When `im.dm.create` is enabled at Run admission, new context-v1 Runs freeze `directMessages:true` in the immutable context budget snapshot, select the autonomous subject and human-agent equality guidance (`teamie-autonomous-subject-v1`, including the safe `TEAMIE_AGENT_PERSONA` envelope when `description` is present), and advertise `im_list_workspace_members` (`GET /api/v1/workspaces/:id/members`) and `im_open_direct_conversation` (`POST /api/v1/workspaces/:id/conversations` with `{"type":"direct","memberIds":[userId]}`). Both tools enforce the Agent's current IM workspace membership, record durable receipts in `runtime_tool_calls`, and bind workspace/conversation source provenance in `ContextArchive` so revoked workspace or conversation membership prevents unauthorized archive reads or cached receipt replay. Opening a direct conversation returns the conversation metadata (`conversationId`) without automatically sending a message; all direct messages are sent explicitly via `im_send_message`.

The private HTTP envelope carries an optional `messageLimit` admission value outside the hashed native model request. Version-6 and version-7 Runs declare 65536; earlier Runs omit it and retain the 128-message native and provider boundary. Multi-line SSE events are bounded while assembling their data, before parsing or retaining a complete event.
